# Focuswilds Implementation Plan

Approved requirements, not a checklist of shipped features. README and this plan remain English. The application supports English and Thai, defaults to English, and is restricted to the owner account.

## Approved cat-care game direction (2026-10-19; planned)

The player collects and cares for cats of different breeds. Use "player", not trainer; cats are individual residents, not evolving monsters or expendable workers. Focus earns money, player experience and items that can be spent on the cats and their shared living space. The mobile PWA, owner-only access and Aseprite requirements remain in force.

The owner-approved setting is now a city and the player's small apartment. "Wilds" means the concrete jungle: focus advances imagined walks through neighborhoods where the player meets stray cats, builds trust over encounters and brings willing cats back to the apartment when capacity permits. This replaces the house-beside-a-garden setting. Focus remains the core activity; city exploration does not require real-world walking or GPS. Review this theme and its portrait compositions before resuming the next-screen implementation.

The current milestone is login only: a warm portrait page, GitHub authentication and owner-only account status. GitHub sign-in uses a same-window authorization return on GitHub Pages and persistent account restoration, with owner-only access. The OAuth callback setting and real-device return/persistence must be verified separately. There is no signed-in game page and no client database access. All gameplay below remains planned. Retired gameplay, assets and schema documentation are removed from the current tree; technical status and production cleanup boundaries are in DEVELOPMENT.md.

### Core loop and focus rewards

1. Choose a task or focus title, select count-up or countdown, and focus. Actual focused time also advances an imagined city walk; no separate walking timer, real-world walking or GPS is required. Retain pause/resume, partial-session recording and recovery; add a separate rest phase. Bound reward-eligible elapsed time and define rest calculation/caps before shipping the new count-up mode. Rest, unattended background rendering and merely reopening the app do not generate focus rewards.
2. Settle verified focus duration into integer money, player XP and an item outcome. Player levels unlock content/capacity; cats gain affection through care rather than focus XP or evolution. No real-money payments, paid pulls or premium currency.
3. Buy or use food, treats, toys and other care items, interact with cats, and improve the room. Show what a care action consumes and its expected affection/mood effect before confirmation.
4. Higher affection increases the chance of helpful cat bonuses. Skipping care across eligible focus rounds can make a cat grumpy and reduce its extra help temporarily. Base focus rewards never decrease. Show the effect before the next round, then use earned resources for care and home progress.

Both completed and partial focus must have a documented reward policy. Use actual eligible duration, not the selected target; splitting/retrying a session or logging the same time through a task must not duplicate base rewards. Define a minimum eligible care/reward round and a duration-based effect budget so repeated tiny sessions cannot farm rewards or accelerate mood penalties. Task checkmarks and tags organize work without paying the same focus time twice. Initial scope includes simple to-dos, subtasks, tags and daily focus goals; habits, time-block routines and self-defined real-life rewards are deferred.

### Cats, affection and mood

- Catalog breed and coat pattern separately with stable IDs and readable art, including mixed-breed domestic cats. Keep each adopted cat's identity, breed/pattern, affection and mood separate from catalog definitions. Initial catalog size, duplicate policy, adoption requirements and numeric balance are implementation decisions, not an unlimited collection promise.
- Begin with one small apartment and one neighborhood route. Focus progress creates city encounters; some cats need several friendly meetings, food or play before adoption. Preserve encounter trust across sessions and absence; meeting a cat is not automatic ownership. Allow one accessible first-cat path and further adoption only when trust and apartment capacity permit. Player progress unlocks additional opportunity/capacity. No forced daily portal visit, real-time breeding/genetics or evolution.
- Give each cat a readable personality and care preferences, and retain where the player first met it as the beginning of its story. Initial personalities, preferences and encounter details are content decisions to define before implementation, not a separate quest system or an additional reward source.
- Affection is the lasting relationship built through care and gifts. Mood is the shorter-term care state. Keep both bounded and visible; high affection raises good-effect probability, while poor mood can reduce the additional bonus. Document how they combine so the UI can explain which outcome is possible.
- Owner-confirmed: missed care advances only through committed eligible focus/play rounds, never wall-clock absence. Closed apps, paused timers, rest, failed writes, duplicate retries, shop browsing and reopening dialogs do not count as missed care. No background decay, daily-login punishment, cat death, escape or loss of adopted cats.
- Record care applied since the previous eligible round and evaluate it once at settlement. Define whether each care type covers one cat or multiple cats; taking an item out of inventory is not care until its validated use succeeds. A failed care action cannot spend an item or improve affection.
- Use appropriate care beyond buying the most expensive gift; define a recoverable basic care option. Negative effects must not create a zero-income trap that prevents the player from caring for cats again. Do not silently add disease, veterinary simulation or passive survival meters.

### Cat effects and balance

- First effect scope is temporary bonuses to newly earned game money, player XP or item chances; grumpiness may reduce the bonus component, never the baseline reward. Do not modify elapsed focus time, user-entered task completion, existing account balances, saved history or real-device behavior. Never remove already earned XP, levels or cats as a mood penalty.
- Show the source cat, effect, affected reward, duration/remaining uses, probability and stacking limit. Show adverse effects clearly before the affected focus round starts; do not reveal an undisclosed penalty only after work is done. A bad-mood roll at settlement therefore affects a subsequent round, not a retroactive deduction.
- Snapshot eligible effects when a focus round starts; changing care selections/room contents or switching devices mid-round must not reroll them. Resolve random outcomes once from a stable operation/session identity, persist the receipt and reuse it on retry. Starting/canceling sessions must not offer free rerolls.
- Set numeric caps, minimum positive reward, overlap rules and rounding policy together with tests. A higher-affection chance is not a guaranteed good effect every round. Basic focus rewards must remain useful when every cat is unhappy.

### Cat room, inventory and shop

- The home screen is the player's small apartment shared with adopted cats. Begin with a window corner, cardboard boxes and basic bowls, then decorate with toys, cat houses/beds, food bowls, water bowls and other cat objects. Display the cats living there and the player's current care/progress; the player level and room upgrades can raise adoption capacity. Expansion improves the apartment's usable space rather than introducing a detached house or outdoor construction system.
- Begin with fixed decoration positions and place/remove actions, not a freeform building editor. Give every functional decoration a disclosed effect; distinguish it from cosmetic objects. Placed objects cannot simultaneously be used up or sold, and removal returns them to inventory without creating duplicates. Never discard a cat when capacity or placement changes.
- Use one bounded catalog of item IDs, prices, allowed actions and effects. The shop buys supported items from the player and sells care items/decorations for game money. Show quantity, unit price, total and any non-sellable status before confirmation. No fluctuating market, player trading or real-money purchase flow.
- Validate integer quantities, sufficient funds/stock, item ownership, capacity and placement at the trusted command boundary. Determine prices and reward effects from catalog data, never caller-supplied totals. Shop purchases/sales, item use, adoption and placement are atomic and idempotent. Prevent buy/sell or placement loops from creating money/items; consumables cannot be sold after use.

### Decisions to calibrate during implementation

Document the initial money/XP rates and item pool, cat breeds and adoption costs, level/capacity thresholds, affection gains, mood tiers and missed-care thresholds, effect chances/caps/durations, room catalog and buy/sell prices. Define task/goal rewards, if any, separately from focus settlement. These are not final values or approved claims of measured balance. Test a zero-money start, all cats unhappy, partial sessions, full capacity, simultaneous tabs, duplicate/lost responses, and purchase/use/sale races before expanding content.

## Mobile PWA priority update (2026-10-19; keyboard implementation pending)

This latest owner-approved direction supersedes earlier landscape-first and page-zoom-preservation requirements. Prioritize an installed portrait mobile experience on iOS and Android before continuing Aseprite asset integration. Keep the approved world, material detail, palette, depth and Aseprite authoring workflow, with cats replacing the survivor-management subject under the latest game direction above. Dated checkpoints in DEVELOPMENT.md describe earlier implementations, not acceptance of this new behavior. The login milestone implements the portrait frame and manifest request. Custom keyboard, settings and focus state remain pending. The owner reported successful real-device installation and zoom checks on 2026-10-19; exact device/OS versions were not recorded.

- Portrait is the layout on every screen. For landscape or square viewports, hide the application and show a portrait-mode notice before React starts, including loading and recovery. Do not rotate the interface or depend on OS orientation locking. Keep the application mounted while hidden so timer state and drafts survive viewport changes. This replaces the earlier automatic rotation approach at the owner's request on 2026-10-19.
- Design the main screen for one-handed touch use, readable scene framing, reachable primary actions and safe areas around notches/home indicators. Keep the shell within one viewport without document scrolling or horizontal overflow. Let long dialogs and the active editing region scroll internally without visible scrollbars. Preserve timer identity/deadline, unsaved drafts, selection and dialog state across resize, rotation, keyboard changes and background/resume; these events must not fetch game state again.
- The ordinary app scale should stay fixed: prevent app-level pinch/double-tap scaling where the browser permits and avoid focus-triggered zoom. Keep editable control text at least 16px. Browser/OS accessibility overrides can still allow zoom; this PWA must not claim an unconditional zoom lock or native-app equivalence on untested devices. Preserve semantic labels, screen-reader navigation, hardware-keyboard operation and readable controls.
- The owner selected a custom in-game keyboard for all first-party text and numeric entry. Build one shared keyboard/editor, styled with GNU Unifont and the game's palette, with Thai/English text layouts and a numeric layout. Use one active editor at a time. Support caret/selection replacement, spaces, case/symbols, deletion that respects user-perceived characters including Thai marks, and clear Done/Cancel actions. Retain existing validation, length limits and disabled states. Keep draft edits local until confirmation; Cancel restores the original value. Read-only/disabled fields must not open an editor. Selection controls and checkboxes remain game-styled choices, not text-keyboard fields.
- Dock the custom keyboard inside the same portrait app frame or active dialog, reserving its space explicitly. Keep the outer shell stationary; bring only the active editing region into view above the keyboard. Do not push the whole page upward, place the keyboard behind a modal, dismiss its parent dialog accidentally or lose edits on rotation. Keep programmatic editing compatible with physical keyboards, IME composition and assistive technology. Suppress the system soft keyboard where supported, with a tested usable fallback when a browser ignores the hint; never leave a field impossible to edit. External provider authentication and OS permission screens cannot use the in-game keyboard.
- Deliver through the existing PWA shell: retain the scoped manifest/start URL, icons and installation guidance, request portrait orientation, and use standalone display where supported. Manifest orientation alone is not a cross-browser lock. Test both browser and installed modes on real iOS/Android devices, including system navigation and app resume. Keep offline startup outside this change; do not add a service worker or promise offline saving merely to label the app a PWA. Existing save-error and timer recovery behavior remains required.
