### Automatically discovered screens

Put each full-screen presentation component in `src/screens/**/*.tsx` with a default export. Its filename becomes the display name, and its folders become the group. A screen requiring props, simulated data or extra states gets a matching sidecar, such as `src/screens/cats/new-arrival.preview.tsx`. It is discovered automatically and supplies the default fixture and optional state components:

```tsx

Keep service orchestration outside screen presentation, and never import Firebase, real account containers or production write operations into preview fixtures. ## Account profile and bounded diagnostics (2026-10-20)

### Current data

- users/{ownerUid}: schemaVersion=1, language=en, timezone=Asia/Bangkok and server createdAt. Created conditionally only when absent; existing fields are never replaced. This does not yet implement account-language loading/Settings or starter-game persistence.
- users/{ownerUid}/logs/account: events array containing at most 100 entries, oldest first, plus server updatedAt. Each entry has id (random UUID), type (sign_in/sign_out_requested/account_error), occurredAt (client UTC timestamp), version (package.json), mode (browser/pwa), environment (local/deployed) and a safe code (none for normal actions; whitelisted auth codes or auth/unknown for errors). - Before authentication, errors stay in sessionStorage key focuswilds.account-errors, capped at 20 code/time pairs. They are not uploaded later. Storage failure is ignored. Unknown provider errors lose their message and become auth/unknown. No tokens, OAuth code/state, URLs, email or full device identity is stored in either history.

The fixed history document replaces the earlier proposed per-event collection: a small bounded diagnostic buffer needs no TTL or cleanup service. Each append sends at most 100 small records (roughly tens of kB), rather than accumulating documents forever. Update-time preconditions prevent concurrent tabs overwriting one another. Only precondition conflicts retry, at most three total read/commit attempts with the same event identity; acknowledgement loss detected on reread does not duplicate an entry. Other failures are not retried. History is best effort: failed requests, contention beyond the bound, closed tabs and offline events can be missing. It is not an authoritative security audit or gameplay ledger.

A fresh OAuth return logs one successful sign_in after completion and owner restoration. Ordinary restored sessions only ensure the profile exists. Sign-out attempts record sign_out_requested while still authenticated and then call Firebase signOut, even if logging fails. This is an intention event, not a claim that sign-out succeeded. Sign-out failures can record a sanitized account_error while the owner remains authenticated. The existing Login / Signing out button stays disabled and guarded during the actual operation. Each storage call, including token/attestation waits and contention retries, is limited to 1500ms; there is no artificial minimum animation time. Profile initialization and sign-in logging run without delaying Home.

### Request and quota budget

Normal page with restored owner: one profile document read; missing profile adds one write. Successful initialization is cached until reload, with concurrent initialization deduplicated. Fresh successful OAuth return adds one history read plus one history write. Sign-out request adds one history read plus one history write. Authenticated error adds the same; unauthenticated errors add zero Firestore operations. No normal reads occur on focus/visibility changes or UI preview. A conflicted event can issue up to three history reads and three commit attempts within the same 1500ms budget; failed attempts are not claimed to be successful writes. Profile race resolution never overwrites the winning record. No post-write read, query, listener, polling, paid service or expiry delete is used. Existing Auth/App Check traffic is separate from these Firestore operations.
